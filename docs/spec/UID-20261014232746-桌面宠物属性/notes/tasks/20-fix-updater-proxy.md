# 20 · fix-updater-proxy（宿主：更新链路必须真正走代理）

| 字段 | 内容 |
| --- | --- |
| **背景** | 用户报告："obox-updater 扩展没有使用代理"。代码级定位（父代理，只读）确认三处缺陷： |
| **缺陷 1** | **`applyProxy()` 是死代码**——`src/main/proxy.ts:234-237` 定义"把代理同时应用到扩展联网与更新两个 session"，但**全仓无调用方** ⇒ "启动时/改设置时让两个 session 处于已配置状态"这条路径从未执行；session 只在某次请求恰好带了 `proxy` 时才被配置。 |
| **缺陷 2** | **下载/安装路径完全没碰代理**——`update:download`（`src/main/updater.ts:317-331`，直接 `autoUpdater.downloadUpdate()`）与 `update:install`（`:333-335`，`quitAndInstall()`）都没有 `applyProxyToSession`；它们是否走代理，纯靠"上一次 check 是否恰好配置过这个 session"这种**偶然状态**。（electron-updater 用的确实是同一 session：`node_modules/electron-updater/out/electronHttpExecutor.js:6,8` 的 `NET_SESSION_NAME = "electron-updater"` = 我们的 `UPDATER_PARTITION`。） |
| **缺陷 3** | **`undefined` 会把 session 重置成直连**——`applyProxyToSession(ses, proxy?)` 在 `proxy` 为假时走 `setProxy({ mode:'direct' })` 并把模块级 `current` 清空（`proxy.ts:196-223`）⇒ 任何"没传 proxy"的调用都在**静默关闭代理**，并让代理认证凭据（`currentProxyCredentials()`，供 `autoUpdater.on('login')`）失效。 |
| **目标** | 让"用户配置了代理"这件事对**所有**更新链路请求（解析源 / 检查 / 下载 / 安装 / 强制重装）**确定生效**，且**不依赖调用顺序**；同时给出可诊断的证据。 |
| **文件所有权** | `src/main/proxy.ts`、`src/main/updater.ts`、`src/main/net.ts`（如需）、`src/preload/index.ts`、`src/renderer/src/main.ts` 与 `src/renderer/src/core/host.ts`（按选定方案接线）、`src/shared/types.ts`（MainApi）、`test/**`（新增/同步）、`docs/update-and-release-verification.md`、`docs/adr/0007-update-provider-and-proxy.md`（追加修订段）。**不含**：`docs/extension-api/**`（除 troubleshooting 若需）、`extensions/**`、根 `package.json`（除必要依赖，预计不需要）。 |
| **实现要求** | ① **让 `applyProxy()` 真正被调用**：渲染进程在**启动时**与**代理设置变化时**把当前代理推给主进程并应用到两个 session。建议方案：新增一条 IPC（例 `proxy:apply`）+ preload 方法 + `MainApi` 类型；渲染进程在 `src/renderer/src/main.ts`（启动）与设置变化订阅处调用。**必须过 `plainProxyConfig`**（reactive Proxy 进 IPC 会抛 `An object could not be cloned.`，见 `core/plainProxy.ts` 与设置页那条历史缺陷）。<br>② **调用点改为"显式覆盖 else 当前配置"**：`updater.ts` 三处（`:64`/`:181`/`:299`）由 `applyProxyToSession(ses, opts.proxy)` 改为 **`applyProxyToSession(ses, opts.proxy ?? currentProxy())`**（`currentProxy()` 已有，`proxy.ts:119`）；**不要**改 `applyProxyToSession` 对 `undefined` 的全局语义——`applyProxy(undefined)` 必须是"用户关掉了代理 ⇒ 直连"，否则关不掉。<br>③ **下载/安装前补配置**：`update:download` 与 `update:install` 在动作前 `applyProxyToSession(updaterSession(), currentProxy())`（该函数按指纹去重，重复调用无开销）。<br>④ **可诊断日志**：更新链路每次动作前打印一条 `[updater] 代理：<proxyRules|direct>（来源：显式/当前配置）`，并在被重置为直连时 `console.warn` 提示"调用方未传代理，已回落当前配置"（若有）。<br>⑤ **凭据链路**：确认 `current` 在被"回落当前配置"时保持一致，代理认证（`autoUpdater.on('login')`）在 check/download 两条路径上都拿得到 `currentProxyCredentials()`。 |
| **验收命令** | ① `npm run typecheck` 0 error；② `npm run lint` 0 error（既有 4 条 warning 不增）；③ `npm test` 全绿（基线 **793 passed + 5 skipped**）；④ **新增单测**（建议 `test/updater-proxy.test.ts`）：a) 调用 `update:resolve-feed`/`update:check`/`update:download`/`update:force-install` 后，**updater session 上应用的是配置的代理规则**而不是 direct（用可注入的假 session 记录 `setProxy` 调用）；b) **不传 proxy 时回落当前配置**（不出现 `mode:'direct'`）；c) **用户关掉代理**（`applyProxy(undefined)`）⇒ 两个 session 都变 direct（这条要防回归：别把"关代理"堵死）；d) 下载路径在"从未 check 过"的情况下也应用了代理 ⇒ 证明不再依赖调用顺序；e) 指纹去重仍生效（同配置重复调用只 `setProxy` 一次）。⑤ **实机验证（必须做，写进回执）**：按 `proxy.ts` 文件头记录的方法——把代理设成**打不通**的 `http://127.0.0.1:9`，点「检查更新」应**失败**且错误为代理类（`ERR_PROXY_CONNECTION_FAILED` 等）、日志里能看到 `[updater] 代理：http://127.0.0.1:9`；再把代理设为可用值（或关闭）⇒ 检查恢复。**注意 `closeAllConnections()` 的存在**：同一进程内切换代理后旧连接必须重建，验证时若出现"切到坏代理仍然成功"，先排查是否复用了旧连接（见 `proxy.ts:213-217` 的实测注释）。⑥ `git status` 只含所有权内文件；**不要**提交（父代理负责 PR）。 |
| **文档同步（AGENTS 强制）** | 改的是主进程能力/代理落地时机 ⇒ `docs/update-and-release-verification.md` §2「代理与证书」补一段"更新链路何时应用代理 + 为什么下载/安装也要显式应用 + 关代理如何生效"；`docs/adr/0007-update-provider-and-proxy.md` 追加"修订"小节（记录 `applyProxy` 从未被调用、`undefined` 的历史语义与本次改动）。若涉及新的 IPC 面，`docs/extension-api/api-reference.md` **不必**改（`proxy:apply` 是宿主内部 IPC，不属扩展 API 面——请在回执里明确这一判断）。 |
| **负向自检** | 代理 URL 非法（`proxyConfigError`）⇒ 按既有规则"warn + 直连"，且日志可见；`noProxy`/`ignoreSSL` 仍生效；代理认证凭据在 check 与 download 两条路径都能取到（构造带 username/password 的配置断言）；`currentProxy()` 在从未配置过时返回 undefined ⇒ 回落直连而非崩溃。 |
